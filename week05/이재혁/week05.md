자바 가상 머신이 제공하는 두 가지 주요 서비스는

- 메모리 관리
- 애플리케이션 코드를 실행하기 위한 쉽고 간단한 컨테이너

> 자바 가상 머신 사양은 자바 구현이 표준에 맞게 동작하기 위해 따라야 할 규칙을 정의.
>

가상 머신 사양에 따르면, 자바 바이트코드는 인터프리터 방식으로 실행되어야 한다.

## 6.1 전통적인 자바 애플리케이션 수명 주기

가장 기본적인 수준에서는 자바 가상 머신을 실행하기 위해 표준 프로세스 실행이 이루어지며, 이는 하나의 단일 프로세스로 동작한다.

- 셸은 자바 가상 머신 바이너리를 찾아 해당 파일을 실행
- 엔트리 포인트 클래스 이름을 포함한 명령줄 인수를 전달
- 이렇게 시작된 새 프로세스는 명령줄 플래그를 분석하고, 플래그에 따라 가상 머신 초기화를 준비(힙 크기, 가비지 컬렉션 설정 등)
- 동시에 실행 중인 머신을 조사하여 시스템 정보를 수집
    - CPU 코어 수, 메모리 용량, 사용 가능한 CPU 명령 집합 등이 포함

자바 가상머신은 이렇게 수집된 세부 정보를 활용해 자신의 설정을 맞춤화하고 최적화한다.

- CPU 코어 수를 기반으로 가비지 컬렉션에서 사용할 스레드 수를 정하거나
- 공용 스레드 풀의 크기를 정한다.

초기 과정 중 하나는 자바 힙을 위해 Xmx 값과 동일한 크기의 사용자 공간 메모리를 예약하는 것이다. + 메타공간 준비(자바 클래스 관련 메타데이터를 저장할 저장소)

그 다음 새로운 스레드에서 보통 JNI_CreateJavaVM 함수를 사용해 가상 머신이 생성된다.

이 과정에서 가비지 컬렉션 스레드나 JIT 컴파일 스레드 같은 가상 머신의 내부 스레드도 함께 시작해야 한다.

대부분의 프로덕션 애플리케이션에서는 시작 단계에서 클래스 로딩, JIT 작업, 그리고 가비지 컬렉션 활동이 급증하면서 이후 애플리케이션이 안정 상태에 도달한다. 안정 상태에 도달하면 다음과 같은 이유로 JIT 작업과 클래스 로딩이 크게 줄어든다.

- 애플리케이션에 필요한 모든 클래스가 이미 로드됨
- 자주 호출되는 메서드가 JIT 컴파일러를 통해 머신 코드로 변환됨

이 설명에서 얻어야 할 전체적인 인상은 매우 동적인 런타임이라는 점이다. 이러한 환경에서 실행되는 애플리케이션은 명확히 정의된 시작 단계를 거친 뒤, 소규모 변화가 지속적으로 발생하는 안정 상태로 전환되는 런타임 특성을 보여준다.

커뮤니티에서는 이러한 전통적인 자바 애플리케이션 수명 주기를 `동적 가상 머신 모드`라고 부른다.

그러나 클라우드 네이티브 자바의 부상과 함께, 컨테이너와 클라우드 환경에서 보다 적합한 새로운 운영 또는 배포 방식에 대한 관심이 증가했다. 이는 여러 면에서 기존의 동적 가상 머신 모드와는 다른 방향으로 나아가고 있다.

## 6.2 바이트코드 해석 개요

자바 가상 머신 인터프리터는 스택 머신으로 동작한다.

- 이는 물리적 CPU와 달리, 계산을 위한 임시 저장 영역으로 레지스터를 사용하지 않는다는 것을 의미한다.
- 대신, 모든 연산에 필요한 값은 평가 스택에 배치됨

자바 가상 머신은 데이터를 저장하기 위해 세 가지 주요 영역을 제공

- 평가 스택: 특정 메서드에 국한되어 사용된다.
- 로컬 변수: 결과를 임시로 저장하며, 역시 메서드에 국한
- 객체 힙: 메서드 간, 그리고 스레드 간에 공유된다.

### 6.2.1 자바 가상 머신 바이트코드 소개

자바 가상 머신의 경우, 각 스택 머신 연산 코드는 1바이트로 표현되므로 이를 바이트코드라고 부른다.

### 6.2.2 간단한 해석기

가장 단순한 형태의 인터프리터는 while 루프의 switch 문으로 구성할 수 있다.

이 예제는 자바 가상 머신 바이트코드의 일부만 실행할 수 있는 아주 작은 범위의 인터프리터다.

- 인터프리터의 execMethod() 는 바이트코드로 작성된 하나의 메서드를 해석한다.

```java
public EvalValue execMethod(final byte[] instr) {
		if (instr == null || instr.length == 0)
				return null;
		
		EvaluationStack eval = new EvaluationStack();
		
		int current = 0;
		LOOP:
		while (true) {
				byte b = instr[current++];
				Opcode op = table[b & 0xff];
				if (op == null) {
						System.err.println("Unrecognized opcode byte: " + (b & 0xff));
						System.exit(1);
				}
				byte num = op.numParams();
				switch (op) {
						case IADD:
								eval.iadd();
								break;
						case ICONST_0:
								eval.iconst(0);
								break;
						
						// ...
						
						case IRETURN:
								return eval.pop();
						case ISTORE:
								istore(instr[current++]);
								break;
						case ISUB:
								eval.isub();
								break;
						// Dummy implementation
						case ALOAD:
						case ALOAD_0:
						case ASTORE:
						case GETSTATIC:
						case INVOKEVIRTUAL:
						case LDC:
								System.out.print("Executing " + op + " with param bytes: ");
								for (int i = current; i < current + num; i++) {
										System.out.print(instr[i] + " ");
								}
								current += num;
								System.out.println();
								break;
						case RETURN:
								return null;
						default:
								System.err.println("Saw " + op + " : can't happen. Exit.");
								System.exit(1);
						}
				}
		}
```

바이트코드는 메서드에서 하나씩 순차적으로 읽히며, 각 코드에 따라 실행이 처리된다. 매개 변수를 포함한 연산 코드의 경우, 매개변수 역시 바이트 스트립에서 읽어들여, 읽기 위치가 항상 정확히 유지되도록 처리된다.

- 임시 연산 값은 평가 스택(EvaluationStack)에 저장되며, 이는 execMethod() 메서드 내부의 로컬 변수로 관리된다.
    - 산술 연산 코드들은 이 스택을 활용해 정수 계산을 수행한다.

## 6.3 핫스팟에서의 JIT 컴파일

JIT 컴파일은 프로그램을 실행 시점에 고성능 기계어로 변환하는 일반적인 기술.

핫스팟과 같은 주류 프로덕션급 자바 가상 머신은 이러한 JIT 컴파일 기술을 주요 성능 향상 도구로 사용한다.

- 프로파일 기반 최적화
    - JIT 컴파일의 효율성을 극대화하기 위해, 런타임에서 수집된 정보를 바탕으로 최적화 과정을 수행.

### 6.3.1 프로파일 기반 최적화

프로파일 기반 최적화의 기본적인 형태는 프로그램 실행 중 데이터를 수집하고 이를 바탕으로 프로파일을 생성하는 것이다. 이 프로그램은 프로그램 내에서 가장 자주 실행되는 부분을 파악하여, JIT 컴파일을 통해 최적화의 이점을 최대화할 수 있는 부분을 결정하는 데 활용된다.

> JIT 서브시스템은 실행 중인 프로그램과 동일한 가상 머신 자원을 공유한다. 따라서 프로파일링 작업과 최적화 수행에 드는 비용은 프로그램의 실행 기간 동안 얻을 수 잇는 성능 향상 효과와 적절히 균형을 맞춰야 한다.
>

### 6.3.2 Klass 워드, 가상 함수 테이블, 포인터 스위즐링 수명 주기

- 운영 체제 입장에서 모든 자바 프로그램은 항상 멀티스레드 환경에서 실행된다.
    - 단일 스레드로 동작하는 자바 프로그램조차도 가상 머신 스레드와 함께 실행되기 때문

핫스팟에서 중요한 스레드 그룹 중 하나는 JIT 컴파일 시스템을 담당하는 스레드들이다.

- 프로파일링 스레드
    - 메서드가 컴파일할 준비가 되었는지 확인하는 프로파일링 스레드
- 컴파일러 스레드
    - 실제 기계 코드를 만든다.

핫스팟의 JIT 컴파일은 메서드 단위로 작동하며, 가상 함수 테이블(vtables)이 그 핵심 역할을 한다.

> 가상 함수 테이블 포인터를 업데이트하는 과정을 포인터 스위즐링(pointer swizzling)이라는 다소 특이한 이름으로 부른다.
>

- 메서드를 새로 호출할 때는 컴파일된 형태로 실행되지만, 이미 실행 중인 스레드는 현재 작업을 해석 모드(느린 실행 방식)로 끝낸 뒤, 다음 호출부터는
  컴파일된 형태를 사용하게 된다.

- 최적화된 기계 코드를 사용할 때, 핫스팟의 최적화가 해당 컴퓨터 아키텍처에서 작동해야 이점이 있다는 점이 중요하다.

### 6.3.3 핫스팟 내부 컴파일러

- 핫스팟 자바 가상 머신에는 JIT 컴파일러가 하나가 아니라 두 개가 들어 있다.
    - 각각 C1, C2로 불린다.

### 6.3.4 코드 캐시

JIT로 컴파일된 코드는 코드 캐시라는 메모리 영역에 저장된다. 이 영역에는 가상 머신의 다른 네이티브 코드도 포함된다.

만약 코드 캐시가 가득 차면 더 이상 JIT 컴파일이 불가능해지고, 컴파일되지 않은 코드는 인터프리터로만 실행된다. 이에 성능이 저하되어 애플리케이션이 최대 성능에 크게 못 미칠 수 있다.

코드 캐시는 내부적으로 미 할당된 영역과 해제된 블록들로 구성된 힙 형태로 구현된다. 네이티브 코드가 제거되면 해당 블록은 자유 리스트에 추가된다. 스위퍼(sweeper)라는 프로세스가 이 블록들을 재활용하는 역할을 한다.

### 6.3.6 JIT 컴파일 로깅

모든 성능 엔지니어가 반드시 알아야 할 중요한 자바 가상 머신 스위치는 다음과 같다.

```java
-XX:+PrintComilation
```

이 설정은 컴파일 이벤트를 표준 출력에 기록하게 하며, 이를 통해 엔지니어는 어떤 코드가 컴파일되고 있는지 기본적으로 파악할 수 있다.

## 6.4 자바 프로그램 실행의 진화

- 자바 애플리케이션의 간단한 수명 주기
    1. 부트스트랩 자바 가상 머신 프로세스
    2. 앱 로드
    3. 준비 과정
    4. 안정 상태
    5. 셧다운

이 모델은 자바에 JIT 컴파일이 도입된 이후로 널리 사용되고 있다.

하지만, 몇 가지 한계가 있으며, 그중 가장 큰 문제는 애플리케이션이 안정 상태에 도달하기까지 실행 속도가 느릴 수 있다는 점이다.

이 전환 시간은 애플리케이션 시작 후 수십 초에 이를 수 있다. 장시간 실행되는 애플리케이션ㄴ에서는 큰 문제가 되지 않는데, 이는 JIT 컴파일된 코드의 이점이 초기 생성 비용을 훨씬 능가한다.

하지만 클라우드 네이티브 환경에서는 프로세스가 훨씬 짧은 시간 동안 실행되는 경우가 많다.

- 자바의 시작 시간과 JIT 컴파일 비용을 감안할 때, 이 비용이 실제로 가치 있는 상황은 무엇인가?
- 자바 애플리케이션의 시작 속도를 높이고 이러한 비용을 줄이기 위해 무엇을 할 수 있을까?
- 많은 클라우드 네이티브 워크로드에서 실제로 필요하지 않은 동적 기능을 지원하기 위해 과도한 리소스를 사용하는 것은 아닌가?

### 6.4.1 AOT 컴파일

컴파일러가 사람에게 읽기 쉬운 소스를 받아 바로 실행 가능한 기계어 코드로 변환하는 과정

AOT 컴파일은 보수적인 선택을 해야 하고, 특정 기능을 사용할 수 있다는 가정이 틀릴 경우 바이너리가 전혀 실행되지 않을 수 있다.

AOT 컴파일된 바이너리는 CPU의 모든 성능을 활용하지 못하며, 성능 향상의 기회를 놓치는 경우가 많다.

## 9.4 자바 특화 고려 사항

컨테이너 환경에서 자바 애플리케이션을 배포할 때 여러 문제가 발생했던 사례를 기반으로, 이를 방지하기 위해 고려해야 할 사항들을 살펴본다.

### 9.4.1 컨테이너와 가비지 컬렉션

렐릭의 연구에 따르면, 현재 자바 애플리케이션의 70% 이상이 컨테이너화 된 환경에 배포되고 있다.

이 컨테이너들 중 약 절반은 단일 CPU만 사용할 수 있도록 설정되어 있다. 이는 문제가 될 수 있다.

자바 가상 머신은 시작 시 가상 머신의 런타임 동작을 제어하는 몇 가지 속성을 동적으로 설정하는데, 여기에는 가비지 컬렉션 설정도 포함된다.

- 기본적으로 G1 컬렉터는 부분적으로 동시성을 지원한다.
- 하지만 동시 컬렉터를 실행하려면 여러 CPU가 필요하다.
- 단일 CPU 머신(단일 코어 컨테이너가 이에 해당)에서는 자바 가상 머신이 자동으로 G1이 효과적으로 작동할 수 없다고 판단하여 Serial이나 SerialOld 컬렉터를 대신 선택한다.

현대 가비지 컬렉터는 동시성을 기반으로 설계되었다. CPU: 1로 설정하면 이러한 제약은 자바 가상 머신이 가비지 컬렉션을 직렬로 실행하게 만들어 애플리케이션의 정지 시간이 길어지고 처리량이 줄어들며 애플리케이션 중단이 더 빈번하게 발생한다.

퍼포먼스 엔지니어로서 이러한 영향을 인지하고, 단일 코어 컨테이너에 배포하는 것이 실질적인 이점을 제공하는 경우에만 이를 선택해야 한다. 레드햇과 마이크로소프트의 연구에 따르면, 단일 코어 컨테이너의 큰 클러스터를 사용하는 것보다 더 적은 수의 컨테이너에 더 많은 CPU를 할당하는 것이 더 효과적일 수 있다.

> 즉, 많은 단일 코어 컨테이너를 배포하는 것은 자원의 낭비일 뿐 아니라 클라우드 인프라 비용을 불필요하게 증가시킬 수 있다. 따라서 특별한 증거가 없는 한, 기본적인 가정은 자바 애플리케이션을 2개 이상의 코어를 사용하는 컨테이너에 배포하는 것이 적합하다는 것리다.
>

### 9.4.2 메모리와 OOMEs

첫 번째 문제는 이전 버전의 자바 가상 머신이 컨트롤 그룹 힌트를 제대로 인식하지 못했다는 점이다.

두 번째 문제는 컨테이너와 자바 가상 머신 간의 설정과 구서에 관한 것이다.

예를 들어, 컨테이너에 1GB의 메모리 할당량을 지정하면 자바 가상 머신 최대 힙 크기는 자동으로 256MB로 설정된다. 컨테이너 내부 또는 다른 프로세스 실행에 필요한 공간을 확보해야 하지만, 이는 자원의 과소 활용을 초래할 가능성이 있다.

최대 힙 크기 -Xmx를 오버라이드하고 성능 테스트를 진행하는 것은 자원 활용도를 극대화하기 위한 좋은 방법이다.
