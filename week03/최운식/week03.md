## 4장 정리: 가비지 컬렉션 기초

### 자바 가비지 컬렉션의 핵심
- 시스템 내 모든 객체의 정확한 수명 주기를 이해할 필요 없이 런타임이 이를 대신 관리한다.
- 더 이상 필요하지 않은 객체를 자동으로 제거하며, 회수된 메모리는 초기화된 후 재사용할 수 있다.
- 프로그래머가 저수준 메모리 관리를 직접 제어하는 대신 GC가 자동으로 처리하는 방식이다.

**첫 출시 당시에는 반발이 높았다**
- 자바가 언어 수준에서 컬렉터의 동작을 제어할 방법을 의도적으로 제공하지 않았다.
- `System.gc()`가 존재하지만 쓸모가 없다.
- 초창기 자바 GC 성능이 좋지 않았다.

**모든 GC 구현이 준수하려는 2가지 규칙**
- 활성 객체는 절대 수집되지 않아야 한다. (훨씬 중요)
- 알고리즘은 모든 가비지를 수집해야 한다.

### Mark and Sweep
기본 형태는 할당된 객체 리스트를 사용해 회수되지 않은 객체들의 포인터를 유지하는 방식이다.

1. 할당된 리스트를 순회하며 마크 비트를 초기화한다.
2. 힙으로의 모든 포인터를 시작점으로 접근 가능한 모든 객체를 찾는다.
3. 도달한 각 객체에 마크 비트를 설정한다.
4. 할당된 리스트를 순회하며 마크 비트가 설정되지 않은 객체에 대해 다음을 수행한다.
   1. 힙에서 해당 객체의 메모리를 회수해 자유 리스트에 다시 추가한다.
   2. 객체를 할당된 리스트에서 제거한다.

활성 객체는 DFS로 탐색되며, 이렇게 만들어진 객체 그래프를 **활성 객체 그래프**라고 한다.

### GC 용어집
- **STW (Stop-The-World)**: GC 사이클이 진행되는 동안 모든 애플리케이션 스레드를 멈춘다. 애플리케이션 코드가 GC 스레드가 보는 힙 상태를 무효화하지 않도록 방지하기 위함이다.
- **동시성 (Concurrent)**: GC 스레드가 애플리케이션 스레드 실행 중에도 동작할 수 있다. G1 컬렉터는 일부 동시성 측면을 갖고 있다.
- **병렬 (Parallel)**: GC 작업을 여러 스레드와 여러 코어를 사용해 실행한다.

### 핫스팟 런타임 소개
자바에는 두 가지 종류의 값만 존재한다.
- 기본 타입 (primitive type): int, byte 등
- 객체 참조

자바는 주소 역참조(포인터) 메커니즘을 제공하지 않는다. 오프셋 연산자(`.`)로 객체 참조에서 필드에 접근하거나 메서드를 호출할 수 있을 뿐이다.

자바의 메서드 호출은 항상 **값 복사** 방식이다. 객체 참조의 경우 힙에 있는 객체의 주소가 복사된다.

### 할당과 수명 주기
GC 동작을 결정하는 2가지 주요 요인은 다음과 같다.
- **할당 속도**: 일정 시간 동안 새로 생성된 객체가 사용하는 메모리 양이며, MB/s로 표기한다.
- **객체의 수명 주기**: 측정이나 추정이 훨씬 어렵다. 실제 애플리케이션에서 객체 수명 주기를 제대로 이해하는 것은 매우 복잡하다.

### 세대 가설
메모리 관리의 중요한 부분은 소프트웨어 시스템 런타임에서 관찰되는 3가지 가설(약한 세대 가설, 강한 세대 가설, 세대 간 참조 가설)을 기반으로 한다.

**약한 세대 가설**

객체의 수명 분포는 이중 분포를 나타낸다. 대부분의 객체는 수명이 짧고, 일부 객체는 훨씬 더 긴 수명을 갖는다.
- GC 힙은 짧은 수명의 객체를 쉽고 빠르게 수집할 수 있도록 구조화해야 하며, 긴 수명의 객체는 짧은 수명의 객체와 분리해야 한다.
- 따라서 힙은 짧은 수명의 영역과 긴 수명의 영역, 2개의 별도 영역을 가져야 하고, 각각 Young GC와 Old GC에서 별도로 수집되어야 한다.
- Young Generation 영역을 자주 청소하는 **Minor GC** 방식을 적용한다.

**강한 세대 가설**

GC 과정에서 살아남은 횟수가 늘어날수록 앞으로도 더 오래 살 가능성이 크다.
- Young Generation에서 여러 번 살아남아 나이(Age)가 찬 객체를 Old Generation으로 승격시켜 관리한다.

**세대 간 참조 가설**

오래된 객체에서 새로운 객체로 참조하는 일은 아주 드물다. 즉, 세대 간 참조 수는 같은 세대 내부의 참조보다 훨씬 적다.
- Old 영역의 객체가 Young 영역의 객체를 참조하는지 검사하려면 Old 영역 전체를 뒤져야 하므로 큰 부하가 걸린다.
- Old → Young 참조는 매우 드물므로 **카드 테이블(Card Table)** 을 이용해 전체가 아닌 해당 테이블만 체크한다.
- 오래된 객체 O의 참조 타입 필드가 수정되면, O가 포함된 카드의 카드 테이블 항목을 더티(Dirty)로 표시한다. 핫스팟은 참조 필드 업데이트 시 간단한 **Write Barrier**로 이를 처리한다.

### 핫스팟의 프로덕션 GC 기술

#### 스레드-로컬 할당
**특징**
- Eden은 힙 영역 중 대부분의 객체가 생성되는 곳이며, 수명이 매우 짧은 객체가 존재한다.
- 다음 GC 사이클 전까지 생존하지 못한 객체는 이 영역을 벗어나지 못한다.

**동작**
- 할당 효율을 개선하기 위해 핫스팟은 Eden을 여러 개의 버퍼로 분할하고, 각 애플리케이션 스레드에 독립적인 영역을 할당해 새 객체를 생성한다.
- 이 영역을 **스레드-로컬 할당 버퍼(TLAB, Thread Local Allocation Buffer)** 라고 한다.
- 더 이상 할당할 TLAB가 없으면 Minor GC(Young Generation 컬렉션)가 발생한다.

**장점**
- 각 스레드가 자신에게 할당된 버퍼에서만 작업하므로, 다른 스레드가 같은 버퍼에서 할당하는 상황을 걱정할 필요가 없다.

#### 반구형 컬렉션
**반구형 대피 컬렉션**
- 이 유형의 컬렉터는 보통 같은 크기의 두 공간을 사용한다.

**핵심 개념**
- 한 공간을 오래 지속되지 않는 객체의 임시 보관 장소로 활용한다.

**장점**
- 짧은 수명의 객체가 Old 영역에 섞이는 것을 방지한다.
- 이를 통해 Full GC 빈도를 줄일 수 있다.

**특징**
- 컬렉터가 활성 반구를 수집할 때 객체는 압축 방식으로 다른 반구로 이동하고, 수집된 반구는 재사용을 위해 비워진다.
- 공간의 절반은 항상 비워진 상태로 유지된다.
- 실제 저장 가능한 메모리의 2배를 반구형 영역에 사용한다.
- 핫스팟 Young 영역의 반구형 공간을 **Survivor(서바이버) 공간**이라고 하며, 일반적인 Eden보다 상대적으로 작다.

#### 클래식 핫스팟 힙
- 각 객체의 세대 카운트(생존한 GC 횟수)를 추적한다.
- 큰 객체를 제외한 대부분의 새 객체는 Eden에 생성되고, 생존한 객체는 두 Survivor 공간 중 하나로 이동한다.
- 일정 기간 생존한 객체를 저장하는 별도 영역을 유지한다. (Young/Old 세대 분리, 중간에 작은 Survivor 공간)

### 병렬 컬렉터 (Parallel GC)
- Young/Old 영역 모두 STW 방식으로 작동한다.
- 처리량(throughput) 최적화에 중점을 둔다.
- 애플리케이션 스레드를 모두 중지한 뒤, 사용 가능한 모든 CPU 코어를 활용해 메모리를 최대한 빠르게 수집한다.
- **ParNew**: Young 영역 GC
- **ParallelOld**: Old 영역 GC
